# Формирование запроса

Задача скилла: превратить черновую формулировку в короткий структурированный запрос, который можно
выполнить без блуждания по проекту, и объяснить пользователю, что изменилось и зачем.

## Почему форма запроса влияет на стоимость

| Часть запроса | Что она заменяет в работе агента |
| --- | --- |
| пути файлов вместо описания «где-то в клиенте» | 3–6 вызовов поиска и чтений |
| указание слоя (Server/Client/Domain/Data/Extension) | чтение правил и файлов ненужных слоёв |
| критерии приёмки одним проверяемым списком | догадки и «проверку на глаз» |
| способ проверки (команда или действие) | самостоятельный выбор проверки и повторные прогоны |
| «не трогаем» | правки по привычке и лишние файлы в диффе |
| объём ≤ 12 строк | сжатие истории и повторное перечитывание запроса |

## Формат сформированного запроса

```
Задача: <что сделать, одной фразой>
Слои: <Server / Client / Domain / Data / Extension — только затронутые>
Файлы: <пути или имена символов из docs/project-map.md>
Критерии: <3–6 проверяемых пунктов>
Проверка: <команда или действие>
Не трогаем: <что исключено>
Решения по умолчанию: <что принято без вопросов>
```

Объём — максимум 12 строк. Если фактов не хватает, не додумывать: в «Решения по умолчанию» записать
принятое допущение, а вопрос задать только если без него выполнение невозможно.

## Порядок работы

1. Прочитать запрос пользователя и сопоставить его со структурой проекта (`docs/project-map.md`).
2. Дозаполнить пустые поля формата фактами из проекта: пути слоёв, реальная команда проверки, критерии.
3. Убрать повторы, рассуждения и историю — оставить только то, что влияет на выполнение.
4. Показать пользователю две вещи: сформированный запрос и 2–4 строки «почему так» (какие поля дали
   экономию, какие assumptions приняты).
5. Выполнять по сформированному запросу; пользователь может его поправить — поправка принимается как
   уточнение, а не как новый запрос.

## Правила

- Не переписывать запрос, если он уже короткий и содержит слои, файлы и критерии: сказать, что
  формировать нечего, и работать как есть.
- Не задавать вопросы, на которые отвечает код проекта; вопрос только про то, чего в коде нет
  (выбор поведения, формат данных, приоритет).
- Для задачи, которая в формате не помещается, — предложить файл задачи в `tasks/` (скилл `task-creator`),
  а не раздувать запрос.
- Отчёт по запросу — 15 строк, секции «реализовано / проверено / затронутые файлы / допущения».

## Пример

Было:
> надо чтобы карточка показывала статус, но она всегда offline, что-то с CORS, поправь

Стало:
```
Задача: health-check карточки выполнять на сервере, клиент показывает статус из ответа API.
Слои: Server (ProbeService), Client (HealthCheckService).
Файлы: Adashboard.Server/Services/ProbeService.cs, Adashboard.Client/Services/HealthCheckService.cs.
Критерии: карточка получает статус по id; таймаут 5 c; редиректы не отслеживаем; клиент не обращается напрямую.
Проверка: dotnet build Adashboard.slnx + запрос к /api/health/check?cardId=N.
Не трогаем: Domain, отображение иконок, расширение.
Решения по умолчанию: статус определяется по CardStatusMode, текст ошибки — text/plain.
```

Почему так: пути файлов убрали поиск по проекту; «Слои» ограничили чтение правил Client и Server;
критерии сделали проверку проверяемой, а не «на глаз»; «Не трогаем» исключило правки Domain;
строки о таймауте и редиректах сняли три решения, которые иначе пришлось бы принимать в ходе работы.
