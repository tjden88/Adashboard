# Рефакторинг доменных моделей и Api: контракты, гранулярные эндпоинты, SiteSettings

## Цель

Разделить persistence-модели (сущности БД) и контракты API, чтобы клиент больше не работал с сущностями напрямую.
Сущности ориентируем на EF Core, а контрактные модели — на UI; их состав и типы данных могут заметно расходиться.
Вместо полного сохранения раскладки (`PUT /api/layout`) дать отдельные эндпоинты для создания, изменения и удаления
карточек и категорий, заменить полное сохранение раскладки на изменение её заголовка и описания, а также добавить
хранение и эндпоинты общих настроек сайта (`SiteSettings`). Результат — чистая основа, на которую затем можно
посадить (уже сломанный) фронтенд.

Фронтенд `Adashboard` в этой задаче **не трогаем** и не пытаемся починить.

## Требования

### Контрактные модели (`Adashboard.Domain`)

- В `Adashboard.Domain.Models` разместить контрактные модели — то, что получает/отправляет фронт:
  `DashboardLayout`, `DashboardCategory`, `DashboardCard`, `SiteSettings`, плюс добавить `DashboardLayoutInfo`.
- Общие типы остаются в `Adashboard.Domain`: enum `UrlScheme`, `CardStatusMode`, `ThemeMode` и справочник `FontAwesomeIcons`.
- Убрать с контрактных моделей атрибуты схемы БД (`[ForeignKey]`, атрибуты навигации). `[MaxLength]` можно оставить
  для валидации входных данных.
- `DashboardCard` (контракт) несёт UI-хелперы `UrlSchemeText`, `GetIconColor`, `GetTextColor` — их использует фронт.
- `SiteSettings` (контракт): `ThemeMode`, `ShowLogo`, `HealthCheckIntervalSeconds`.
- `DashboardLayoutInfo` (контракт): `Title`, `Description` — тело запроса на изменение инфо раскладки.
- В `Adashboard.Domain` не должно остаться ничего, что относится к хранению данных (EF-сущности, навигации БД).
- Модели максимально ориентированы на UI: не содержат избыточных для клиента данных, используют понятные человеку типы
  и удобны для валидации. Разрешено добавлять read-only вспомогательные свойства и методы, вычисляемые из собственных
  данных модели (например, `UrlSchemeText`, `GetIconColor`, `GetTextColor`).
- Состав и типы моделей намеренно могут расходиться с сущностями. В ходе реализации разрешено добавлять, изменять и
  удалять свойства моделей — исполнитель решает по каждой сущности отдельно, что именно модели нужно для удобного UI,
  а что является лишней деталью хранения.

### Сущности и хранение (`Adashboard.Api`)

- Создать `Adashboard.Api/Data/Entities` (namespace `Adashboard.Api.Data.Entities`) и перенести туда сущности БД,
  добавив суффикс `Entity`: `DashboardLayoutEntity`, `DashboardCategoryEntity`, `DashboardCardEntity`,
  `SiteSettingsEntity`. Перенести поля, навигации и атрибуты схемы (`[MaxLength]`, `[ForeignKey]`).
- Сущности максимально ориентированы на EF Core: двусторонние навигационные свойства, атрибуты схемы и/или конфигурация
  в `OnModelCreating`, типы полей, удобные для БД. Состав и типы сущностей могут отличаться от моделей — это нормально.
- `DashboardDb`: DbSet'ы `Layouts`, `Categories`, `Cards` перевести на `*Entity`; добавить DbSet для `SiteSettingsEntity`.
- Настроить `SiteSettingsEntity` как одиночную строку (идентификатор `Id = 1`).
- `DbInitializer`: перевести на `*Entity`; сохранить текущее стартовое наполнение раскладки и дополнительно
  сидировать настройки по умолчанию (`ThemeMode.Auto`, `ShowLogo = true`, `HealthCheckIntervalSeconds = 30`),
  если записи настроек нет. Наличие раскладки по-прежнему означает, что наполнение уже выполнялось.

### EF Core и миграции

- Пользователь удалил прежнюю миграцию и файл БД, поэтому создать **одну новую начальную миграцию** под новую схему
  (`Layouts`, `Categories`, `Cards`, `SiteSettings`) без таблицы `CardImage`.
- Миграции применяются при старте (существующий механизм `DbInitializer`). Старых данных для переноса нет.

### Маппинг (Mapperly)

- Подключить в `Adashboard.Api` библиотеку `Riok.Mapperly`.
- Маппинг `*Entity` ↔ контрактные модели реализовать source generator'ом: объявить `[Mapper] partial class` с
  partial-методами на каждый переход (сущность → модель и модель → сущность). Код маппинга генерируется на сборке,
  руками маппинг не писать; вложенные коллекции (раскладка → категории → карточки) маппятся автоматически.
- Расхождения сущностей и моделей описывать явно: переименованные/разнотипные поля — атрибутом `[MapProperty]`
  (при необходимости — вспомогательным partial-методом), лишние члены — `[MapperIgnoreSource]`/`[MapperIgnoreTarget]`.
  Read-only вычисляемые свойства моделей Mapperly как target не трогает — это ожидаемо.
- Маппинг выполняется на стороне Api; контроллеры и сервисы отдают контрактные модели, сущности наружу не уходят.
- Если возникнут непреодолимые проблемы с генератором Mapperly (диагностики, несовместимость с `net10.0`), описать их
  в отчёте и согласовать замену; молча вводить ручной маппинг или другую библиотеку нельзя.

### Эндпоинты

- `LayoutController` (`/api/layout`):
  - оставить `GET /api/layout` — возвращает `DashboardLayout` (с категориями и карточками);
  - удалить `PUT /api/layout`;
  - добавить `PUT /api/layout/info` — тело `DashboardLayoutInfo`, меняет заголовок и описание раскладки `Id = 1`,
    ответ `204 No Content`, пустое/некорректное тело — `400 Bad Request`.
- `CategoriesController` (`/api/categories`):
  - `POST` — создание категории, ответ `201 Created` с созданной моделью (нужен назначенный `Id`);
  - `PUT /{id}` — изменение, `204 No Content`; `404 Not Found`, если категории нет;
  - `DELETE /{id}` — удаление (карточки категории удаляются каскадно), `204 No Content`; `404 Not Found`, если нет.
- `CardsController` (`/api/cards`, рядом с существующими эндпоинтами изображения):
  - `POST` — создание карточки (модель содержит `DashboardCategoryId`), `201 Created` с созданной моделью;
    `400`, если категория не указана; `404`, если категория не найдена;
  - `PUT /{id}` — изменение, `204 No Content`; `404`, если карточки нет;
  - `DELETE /{id}` — удаление, `204 No Content`; `404`, если карточки нет;
  - существующие `POST /{cardId}/image`, `POST /{cardId}/image/from-url`, `DELETE /{cardId}/image` сохранить
    (допустим только перевод их внутренностей на сущности `*Entity`).
- `SettingsController` (`/api/settings`):
  - `GET` — возвращает `SiteSettings`; если записи нет, возвращает значения по умолчанию;
  - `PUT` — обновляет `SiteSettings`, `204 No Content`; недостоверные данные (например, `HealthCheckIntervalSeconds <= 0`) — `400`.
- Переупорядочивание (drag & drop) в этой задаче **не реализуем**: отдельных reorder-эндпоинтов не добавляем.
  Поля `Order`/`Position` можно задавать при создании и изменении через обычные модели.

### Сервисы

- Заменить `DashboardLayoutService` на `LayoutService`: чтение раскладки, изменение инфо, CRUD категорий и карточек,
  маппинг entity ↔ контрактная модель через Mapperly.
- Добавить `SiteSettingsService`: чтение и обновление настроек.
- Сервисы принимают и возвращают контрактные модели; сущности БД наружу не отдают.
- Для сервисов и инфраструктурных классов — XML-комментарии (класс, публичные методы). Логирование по правилам проекта:
  русский язык, структурированные параметры, лог начала/успешного завершения и `LogWarning` для нетипичных сценариев.

### Прочее

- `ProbeService` продолжает работать: формирование URL из схемы и адреса карточки сохраняется (через хелпер на сущности
  или общий extension-метод для `UrlScheme`).
- Публичные контракты probe-эндпоинтов и image-эндпоинтов не меняем.
- Не логировать секреты; проверку схемы URL сохранить как есть.
- Ссылку на проект фронтенда в `Adashboard.Api.csproj` не возвращать (она уже убрана, чтобы Api собирался независимо
  от сломанного фронта).
- Комментарии в коде — только на русском языке.

## Критерии приёмки

- [ ] `dotnet build Adashboard.Api` и `dotnet build Adashboard.Domain` проходят без ошибок.
- [ ] Сущности `*Entity` находятся в `Adashboard.Api/Data/Entities` и ориентированы на EF Core (навигации, атрибуты
      и/или конфигурация); в `Adashboard.Domain` остались только контрактные модели, общие enum'ы и справочник иконок,
      причём модели ориентированы на UI и могут отличаться от сущностей составом и типами.
- [ ] Создана одна новая начальная EF-миграция под новую схему (без `CardImage`); при старте БД создаётся и наполняется
      стартовой раскладкой и настройками.
- [ ] `GET /api/layout` возвращает контрактную модель раскладки с категориями и карточками.
- [ ] `PUT /api/layout/info` меняет заголовок и описание; `PUT /api/layout` отсутствует.
- [ ] `POST`, `PUT`, `DELETE` по `/api/categories` и `/api/categories/{id}` работают; `POST` возвращает созданную
      категорию с назначенным `Id`, удаление категории каскадно удаляет её карточки.
- [ ] `POST`, `PUT`, `DELETE` по `/api/cards` и `/api/cards/{id}` работают; `POST` возвращает созданную карточку с `Id`;
      существующие эндпоинты изображения карточки не сломаны.
- [ ] `GET /api/settings` и `PUT /api/settings` работают; при первом запуске настройки засеяны значениями по умолчанию.
- [ ] Маппинг entity ↔ контрактная модель реализован через Mapperly (source generator); ручного маппинга в коде нет.
- [ ] Все новые комментарии и сообщения логов — на русском языке.
