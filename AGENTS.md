# AGENTS.md

## О проекте

Это dashboard-приложение для личного использования, по концепции похожее на Dashy или Homarr.

- UI-фреймворк: Blazor
- Целевая платформа: .NET 10
- Основная идея: настраиваемая стартовая страница с виджетами, ссылками, сервисами, группами, индикаторами состояния и различными вариантами раскладки

Перед внесением изменений изучай структуру решения, проекты и существующие соглашения. Не вводи новую архитектуру, если в проекте уже есть подходящее решение.

## Главные принципы

- Главный приоритет: скорость разработки и получение работающего результата.
- Не создавай монструозную архитектуру, избыточные абстракции и инфраструктуру «на будущее» без конкретной необходимости.
- Выбирай самое простое решение, которое понятно поддерживать и которое решает текущую задачу.
- Не усложняй код ради идеальной архитектуры или формального соответствия шаблонам enterprise-разработки.
- Сохраняй существующие рабочие соглашения проекта, если нет веской причины их менять.
- Держи компоненты и методы небольшими, но не создавай отдельные слои и сервисы без практической пользы.
- Используй асинхронные API и отмену операций там, где это действительно необходимо.
- Соблюдай nullable reference types.
- Не меняй молча публичное поведение, формат сохранённых данных или конфигурацию.
- Не добавляй зависимости без явной пользы.

## Язык общения

- Общайся с пользователем только на русском языке.
- Планы, уточняющие вопросы, сообщения о ходе работы и итоговые отчёты пиши на русском языке.
- Названия классов, методов, свойств и переменных оставляй на английском языке в соответствии с соглашениями .NET.
- Технические термины и названия API можно оставлять на английском языке, если это повышает точность.

## Требования к комментариям

- Все комментарии в коде пишем только на русском языке.
- Комментарии должны объяснять нетривиальную логику и причины решений, а не дублировать очевидный код.
- Для сервисов и инфраструктурных классов обязательны XML-комментарии:
  - комментарий у класса;
  - комментарии у всех публичных методов;
  - комментарии у публичных свойств, если их назначение неочевидно.
- Внутренние (`private`) методы сервисов комментируем, если без комментария сложно понять цель метода.
- Не добавляем избыточные комментарии к простым геттерам/сеттерам и тривиальным операциям.

## Требования к логированию сервисов

- Для операций в сервисах обязательно добавляем логирование через стандартный `ILogger` из ASP.NET.
- Сообщения логов пишем только на русском языке.
- Минимум для каждой публичной операции сервиса:
  - лог начала выполнения;
  - лог успешного завершения;
  - предупреждение (`LogWarning`) для нетипичных, но ожидаемых сценариев.
- Не пишем в логи секреты, токены, пароли, cookies, connection string и чувствительные payload.
- В сообщениях логов используем структурированные параметры (`{Name}`), а не конкатенацию строк.

## Правила Blazor

- Следуй hosting-модели, которая уже используется в проекте. Не переключай Blazor Web App, Server, WebAssembly или Auto render mode без явного требования.
- Учитывай границы render mode при внедрении сервисов, работе с браузерными API и управлении состоянием.
- Используй параметры компонентов и `EventCallback`, а не прямой доступ к состоянию дочерних компонентов.
- Освобождай подписки, таймеры, cancellation tokens и ресурсы JavaScript interop.
- Не допускай лишних перерисовок и повторных сетевых запросов.
- Для асинхронных виджетов явно обрабатывай состояния загрузки, пустого результата, ошибки и повторной попытки.
- Используй семантический HTML, клавиатурную навигацию, заметный focus и понятные подписи элементов управления.
- Сохраняй корректную работу на desktop, tablet и mobile.
- Не используй JavaScript, если задачу можно просто решить средствами Blazor или CSS. Необходимый JavaScript interop изолируй в небольшом модуле или сервисе.

## Предметная область dashboard

- Считай конфигурацию dashboard пользовательскими данными, а не исполняемым кодом.
- Делай модели виджетов, плиток, групп, ссылок, раскладки, темы и health-check явными и понятными.
- Проверяй конфигурацию на границе приложения и показывай понятные сообщения об ошибках.
- Ошибка одного виджета не должна ломать весь dashboard.
- Используй стабильные идентификаторы элементов, а не отображаемые имена или индексы списков.
- Сохраняй пользовательские настройки при добавлении новых свойств конфигурации.
- Для периодического обновления учитывай интервалы, таймауты, повторы, кэширование и параллельные health-check.
- Не показывай в UI секреты, внутренние URL, stack trace и чувствительные детали health-check.

## Архитектура

- Компоненты UI отвечают за отображение и взаимодействие с пользователем.
- API-вызовы, хранение данных, health-check и внешние интеграции размещай в сервисах только тогда, когда это упрощает код.
- Используй dependency injection для прикладных сервисов.
- Разделяй DTO, domain и persistence models только при реальной необходимости.
- Не создавай отдельные слои, generic-репозитории и сложные паттерны без конкретной задачи.
- Разделяй конфигурацию dashboard, данные состояния виджетов и административные функции настолько, насколько это нужно текущему приложению.
- Для внешних HTTP-сервисов используй `HttpClientFactory` или typed clients.
- Для внешних запросов задавай таймауты и поддерживай отмену, если операция может выполняться долго.

## Безопасность

- Считай внешние URL, подписи, иконки и настройки виджетов недоверенными данными.
- Проверяй разрешённые схемы URL и не отображай непроверенный HTML.
- Авторизацию проверяй на сервере; скрытие кнопки в UI не является защитой.
- Никогда не добавляй в Git пароли, токены, connection strings и приватные ключи.
- Не записывай в логи access tokens, cookies, пароли и полные чувствительные payload.
- Учитывай риск SSRF, если сервер обращается к URL, указанному в пользовательской конфигурации.
- Используй antiforgery и существующий в проекте механизм аутентификации и авторизации.

## Проверка изменений

Тесты в этом личном проекте не пишем и не поддерживаем, если пользователь явно не попросит об этом отдельно.

Перед завершением изменения:

1. Запусти используемые в проекте форматтеры или analyzers, если это не требует значительных дополнительных настроек.
2. Просмотри diff на случай случайных изменений, секретов, generated-файлов и нежелательных изменений конфигурации.

Не выполняй разрушающие команды для базы данных или файловой системы без явного разрешения. Не создавай и не применяй миграции без запроса пользователя или явной необходимости для задачи.

## Порядок работы

- Для большой задачи сначала изучи проект и составь короткий план.
- Перед редактированием определи затронутые компоненты, сервисы, модели и конфигурацию.
- Вноси минимальное связное изменение, которое решает задачу.
- Переиспользуй существующие компоненты дизайна, CSS-переменные, иконки и соглашения.
- Не добавляй документацию, sample configuration и дополнительные абстракции без практической необходимости.
- После работы сообщи, что изменено, какие проверки выполнены и какие допущения остались.
