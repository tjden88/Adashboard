# AGENTS.md — ядро правил

Правила проекта. Подробные разделы вынесены в скиллы: в контекст попадает только ядро (этот файл)
и скилл, соответствующий типу изменения. Скилл выбирается по задаче, а не читается «на всякий случай».

## О проекте

Личный dashboard (концепция близка к Dashy/Homarr): настраиваемые страницы с категориями, карточками,
виджетами, индикаторами состояния.

| Проект | Роль | Ключевые файлы |
| --- | --- | --- |
| `Adashboard.Client` | Blazor WebAssembly (.NET 10), standalone WASM | `Program.cs`, `Services/AppStateService.cs`, `Components/Pages/Home.razor` |
| `Adashboard.Server` | ASP.NET Web API (.NET 10) + хост статики клиента | `Program.cs`, `Controllers/`, `Services/`, `Mapping/MapperConfig.cs` |
| `Adashboard.Domain` | контрактные модели, enum'ы, справочники | `Contracts/`, `ReadModels/`, `Reference/DomainConstants.cs` |
| `Adashboard.Data` | EF Core: контекст, сущности, миграции | `DashboardDb.cs`, `DbInitializer.cs`, `Entities/` |
| `Adashboard.Extension` | Manifest V3 (TypeScript + Vite), вне `Adashboard.slnx` | `src/api.ts`, `src/popup.ts`, `public/manifest.json` |

## Как собирать данные о проекте

1. **Индекс вместо чтения файлов:** `docs/project-map.md` — искать имя символа, читать только файл из найденной
   строки и только по месту. Регенерация: `powershell -File scripts/project-map.ps1` (после изменения структуры).
2. **API-контракт:** `openapi/Adashboard.Server.json` — имена методов клиента ищутся по `operationId`.
3. Файл индекса целиком не читать: он нужен для поиска, в контекст берётся найденная строка.
4. Правила не перечитывать: они уже здесь и в выбранном скилле.

## Команды проверки

- `dotnet build Adashboard.slnx` — сборка решения.
- После изменения API нужны **две сборки**: первая обновляет OpenAPI-спецификацию, вторая пересобирает Refit-клиент.
- `npm run typecheck` и `npm run build` — проверки расширения (отдельный npm-проект).
- Тестов в проекте нет; проверка — критерии приёмки задачи плюс сборка.

## Правила, которые нужны всегда

- Общение, комментарии, сообщения логов — только на русском. Имена классов и методов — на английском.
- XML-комментарии: ровно `/// <summary>…</summary>`, без `<param>`, `<returns>` и прочих тегов.
- Ожидаемые ошибки в сервисах — `OperationResult` (`Result.Success()`, `Result.Failure(...)`), не исключения.
- Интерфейсы для собственных сервисов не заводим: внедряем конкретные реализации.
- Nullable reference types; async и отмена там, где операция может быть долгой.
- Не менять молча публичное поведение, формат сохранённых данных, конфигурацию. Не добавлять зависимости без явной пользы.
- Миграции не создавать и не применять без запроса пользователя.
- Строки не переносим, если они меньше 200 символов.
- Отчёт о работе: максимум 15 строк, секции «реализовано / проверено / затронутые файлы / допущения».
